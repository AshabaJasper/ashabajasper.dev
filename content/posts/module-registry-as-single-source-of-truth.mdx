Jasper OS is my private life dashboard: tasks, habits, goals, money, notes, documents, reviews and a good deal more, in one Next.js app that only I sign in to. For a while, the question "what is this app made of?" had several answers, and they did not agree.

There were four navigation lists maintained by hand: the sidebar, the quick links on the overview, the quick add menu and the tabs inside Finance. There was an `AccentKey` union for page colours that had to change in step with the sidebar. And three smaller registries, for reports, calculators and integrations, had each invented their own idea of what a module was. Every new area meant editing all of them, and keeping them in agreement was a matter of memory.

The fix was to stop maintaining lists. There is now exactly one, and everything else is derived from it.

## The registry is pure data

The list lives in `src/lib/modules/registry.ts`. Each entry describes one module: its slug, title, route, sidebar group, icon, accent, description, whether it is on by default, and how it relates to other modules.

```ts title="src/lib/modules/registry.ts"
export interface ModuleDefinition {
  slug: string;
  title: string;
  shortTitle?: string;
  href: string;
  group: ModuleGroupKey;
  icon: IconKey;
  /** Index into AVATAR_PALETTE. */
  palette: 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7;
  description: string;
  /** Core shell: cannot be switched off. */
  alwaysOn?: boolean;
  defaultEnabled: boolean;
  /** sidebar = own nav entry; tab = lives inside its parent; hidden = feature flag only. */
  nav: "sidebar" | "tab" | "hidden";
  /** A child module is on only while its parent is on. */
  parent?: string;
  /** Other modules this one needs. Plain strings, validated by test. */
  requires?: readonly string[];
  quickAdd?: readonly QuickAddEntry[];
  quickLink?: boolean;
}
```

The array is declared `as const satisfies readonly ModuleDefinition[]`. That does two jobs at once: the compiler checks every entry against the interface, and the literal slugs survive, so `ModuleSlug` is a real union type rather than `string`.

```ts title="src/lib/modules/registry.ts"
export const MODULES = [
  {
    slug: "tasks",
    title: "Tasks",
    href: "/tasks",
    group: "now",
    icon: "ListTodo",
    palette: 2,
    description: "Everything you intend to do, linked to goals, projects and people.",
    defaultEnabled: true,
    nav: "sidebar",
    quickAdd: [{ label: "Task", href: "/tasks?new=1" }],
    quickLink: true,
  },
  // ...42 more
] as const satisfies readonly ModuleDefinition[];

export type ModuleSlug = (typeof MODULES)[number]["slug"];
```

What matters most is what the file does not import at runtime. No React, no Lucide, no Prisma. Because it is plain data, the same file loads in a server component, a client component, a cron job and a Vitest run without any of them dragging in something they should not.

### What derives from it

The registry holds 43 modules: 35 with their own sidebar entry, six that live as tabs inside a parent, and two hidden ones that act as feature switches on the Today page. None of the surfaces below is maintained by hand any more.

| Surface | Where it is derived |
| --- | --- |
| Sidebar groups | `NAV_GROUPS` in `src/lib/navigation.ts` |
| Quick add menu | `QUICK_ADD_ITEMS`, flattened from each module's `quickAdd` |
| Shortcut chips on the overview | `QUICK_LINKS`, every module with `quickLink: true` |
| Page accents | `AccentKey = ModuleSlug`, coloured from each module's `palette` |
| Which module owns a URL | `moduleForPath()`, longest `href` prefix wins |
| On and off switches in Settings | the same list, grouped and rendered as toggles |

The navigation file opens with a comment that says it plainly: to add, move or rename a nav entry, edit the registry, never this file.

## Icons as strings, not components

A Lucide icon is a React component, which means it is a function, and functions cannot cross the server/client boundary as props. A server layout cannot hand a client sidebar a list of icons.

So the registry stores an `IconKey`, a string, and a small file resolves it.

```ts title="src/lib/modules/icons.ts"
import { ListTodo, Repeat, Sun, Wallet, type LucideIcon } from "lucide-react";

export const MODULE_ICONS = {
  ListTodo,
  Repeat,
  Sun,
  Wallet,
  // ...one entry per icon the registry uses
} satisfies Record<string, LucideIcon>;

export type IconKey = keyof typeof MODULE_ICONS;

export function moduleIcon(key: IconKey): LucideIcon {
  return MODULE_ICONS[key];
}
```

`icons.ts` has no `"use client"` directive, so both sides can import it and look the icon up locally. A typo in the registry is a type error, because `icon` must be a key of `MODULE_ICONS`. The same idea runs through the whole app: the server sends slugs and keys, and the client rebuilds what it needs. The layout passes the modules provider `enabledSlugs: string[]` and nothing richer.

## Resolving what is actually on

Modules relate to each other in two ways. A `parent` means a child follows its parent: a tab inside Finance is only on while Finance is on. A `requires` list is a hard dependency: the time blocks on Today need Tasks, and the weekly planner needs time blocks.

That makes "is this module on?" a fixpoint question rather than a lookup. `resolveEnabled` in `src/lib/modules/resolve.ts` starts with every module I want on, then keeps removing anything whose parent or requirements are missing until nothing changes.

```ts title="src/lib/modules/resolve.ts"
export function resolveEnabled(overrides: ModuleOverrides): Set<ModuleSlug> {
  const on = new Set<string>(
    MODULE_LIST.filter((m) => wants(m.slug, overrides)).map((m) => m.slug)
  );
  let changed = true;
  while (changed) {
    changed = false;
    for (const slug of [...on]) {
      if (needs(slug).some((dep) => !on.has(dep))) {
        on.delete(slug);
        changed = true;
      }
    }
  }
  return on as Set<ModuleSlug>;
}
```

Chains behave without special cases. Switch Tasks off and the time blocks go quiet, which takes the planner with them. Each module's own switch is remembered, so they all come back when Tasks does.

Three helpers in the same file keep the settings screen honest. `enableClosure(slug)` returns a module plus everything it needs, so turning on the planner turns on its dependencies in one click. `dependentsOf(slug)` returns everything that would stop working, so the screen can warn before something is switched off. `presetOverrides(key)` expands a preset such as Essentials or Focus into a full override map.

All of it is pure and tested. The registry test checks that every `parent` and `requires` points at a real module and that the dependency graph has no cycles.

## Ownership maps that fail typecheck

The registry answers "what modules exist?" The harder question is "who owns this cross-cutting thing?" An alert about a domain expiring, a section of the AI context, a line in a digest: when a module goes off, all of those should go quiet with it.

`src/lib/modules/ownership.ts` answers that with exhaustive maps.

```ts title="src/lib/modules/ownership.ts"
import type { AlertType } from "@prisma/client";
import type { BrainSection } from "@/lib/brain/sections";
import type { ModuleSlug } from "./registry";

export const ALERT_MODULE: Record<AlertType, ModuleSlug> = {
  SUBSCRIPTION_RENEWAL: "subscriptions",
  DOMAIN_EXPIRY: "infrastructure",
  TASK_DUE: "tasks",
  INBOX_PILEUP: "inbox",
  CUSTOM: "attention",
  // ...every AlertType in the schema
};

export const BRAIN_SECTION_MODULE: Record<BrainSection, ModuleSlug> = {
  goals: "goals",
  tasks: "tasks",
  notes: "notes",
  // ...every brain section
};
```

Because the key type is the whole `AlertType` union generated by Prisma, adding a value to the enum makes this file fail typecheck until the new alert has an owner. That is the entire trick: I do not have to remember, because the compiler remembers for me. The imports are type-only, so nothing here pulls Prisma or the AI context builder in at runtime.

The consumers are short filters. `filterAlertsByModule` drops alerts whose owner is off, with one deliberate exception: reminders I wrote by hand always stay, because I asked for them explicitly.

<Note title="Shared owners are a design decision">
Two alert types, upcoming commitments and upcoming events, span several areas. Rather than pick one area arbitrarily, they belong to the always-on Attention module, and each individual item is gated by its own area's module where it is built. A comment in the map says so, which matters more than the mapping itself.
</Note>

## Reading state once per request

My switches live in a single settings row, key `modules`, with the value `{ v: 1, overrides }`. The override map is sparse: a module with no entry falls back to its `defaultEnabled`.

```ts title="src/lib/modules/server.ts"
export const getModuleState = cache(async (userId: string): Promise<ModuleState> => {
  const stored = await getSetting<unknown>(userId, MODULES_SETTING_KEY, null);
  const overrides = sanitize(stored);
  return { overrides, enabled: resolveEnabled(overrides) };
});
```

Two choices here are worth explaining.

**It takes `userId` explicitly.** The attention engine, the digests, the automation rules and the AI context API all run from cron jobs or key-authenticated routes with no session. A helper that read the session would work in pages and quietly break everywhere else.

**It is wrapped in React `cache()`.** The layout, the attention scan behind the bell and the page itself can all ask for module state in the same request. `cache()` makes that one query however many consumers ask.

The sparse map has a useful consequence: a module added next month simply picks up its default, with no migration and no backfill. A preset is one atomic write of an explicit value for every switchable module. `sanitize` drops anything that is not a boolean, and resolution ignores slugs the registry no longer knows, so an old stored value cannot break a newer build.

## Off means quiet, never deleted

This was the rule I cared about most. Switching a module off is a statement about attention, not about data.

| Surface | When the module is off |
| --- | --- |
| Sidebar, quick add, overview shortcuts | Gone |
| Its own page | Still opens, under a banner with a link to the module settings |
| Alerts, digests and nudges | Filtered out |
| Automation rules it owns | Do not run |
| AI context | Its sections are dropped |
| Search, reports, calendar feed | Its results, datasets and sources are skipped |
| The data itself | Untouched |

The page still rendering is deliberate. A 404 would look exactly like lost data. Instead the banner says the module is switched off, that it is hidden from navigation, alerts and digests, and that the data is kept exactly as it is. Switching it back on restores everything.

## The test that guards the database

The registry keeps the interface honest. A second pure file, `src/lib/data/manifest.ts`, does the same for the database. Every Prisma model is classified once: a `root` with its own reset and export rules, a `child` that cascades from a root, a `system` table such as the audit log, or `dead` schema with a written reason.

Before the manifest, the danger-zone reset and the JSON export each kept their own hand-written list of tables, and both had drifted: the reset skipped a batch of newer tables and the export silently left some out. Now both loop over the manifest, and `tests/data-manifest.test.ts` parses the Prisma schema and compares names.

```ts title="tests/data-manifest.test.ts"
it("classifies every model in the schema, and nothing else", () => {
  const schemaNames = models.map((m) => m.name).sort();
  const manifestNames = Object.keys(DATA_MANIFEST).sort();
  expect(manifestNames).toEqual(schemaNames);
});
```

Other cases in the same file check that a `child` really has an `onDelete: Cascade` relation to its parent, that every child is included in its root's export, and that any user-scoped table left out of the reset says why.

## The recipe

All of this is written down in `docs/MODULES.md` as a numbered recipe for adding a module: schema and migration, manifest entry, registry entry, icon key, ownership maps, alerts with a privacy tier, validators, plain business logic that takes `userId`, server actions, the page, and the optional extras for AI context, search, reports and the calendar feed.

The recipe ends with the tests that guard it, and that is the part I would keep if I had to throw the rest away. A checklist in a document gets skipped. A checklist where most skipped steps fail typecheck or a test does not.

## Trade-offs and what I would change

**The registry file is long.** At 43 entries it runs to several hundred lines. That is acceptable because each entry is boring and the file is mostly appended to, but next time I would split the types and helpers from the data sooner.

**`parent` and `requires` are plain strings.** `ModuleSlug` is derived from the array itself, so the array's own entries cannot use it, and a test catches bad references instead. It works, but it is a runtime guard for something I would rather the compiler checked.

**Off is not private.** Hiding a module is about focus. It does not encrypt anything or change who can read the data, and I try never to mistake one for the other.

**Derivation hides wiring.** When everything flows from one list, a new reader cannot grep for the sidebar entry they see. The comments at the top of `navigation.ts` and `registry.ts` exist to point people back to the source.

## Takeaway

If several parts of an app describe the same set of things, make one pure list the source and derive the rest. Use exhaustive `Record` types for anything cross-cutting so new cases cannot slip through, keep the list free of runtime imports so every environment can load it, and make switching off a quiet, reversible act.
