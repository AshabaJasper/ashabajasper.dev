Open a browser console and type `0.1 + 0.2`. The answer is `0.30000000000000004`. That is not a JavaScript bug, it is how binary floating point works, and it is harmless right up until the number is the balance of a savings account.

Jasper OS is the private dashboard I use to run my own life admin, and money is the part I trust least to "mostly work". It handles Ugandan shillings and US dollars, accounts from mobile money to SACCO shares, loans, and a set of calculators. This post covers the handful of rules that keep those numbers honest.

## Store integers, in the smallest unit you actually use

Every ledger amount in Jasper OS is an integer in **minor units**. For US dollars that means cents, so USD 12.50 is stored as `1250`. For Ugandan shillings the exponent is zero: the shilling has no sub-unit in practical use, so UGX 45,000 is stored as `45000`.

```ts title="src/lib/calculations/money.ts"
export const CURRENCY_EXPONENT: Record<Currency, number> = {
  UGX: 0,
  USD: 2,
};

export function toMinor(amount: number, currency: Currency): number {
  return Math.round(amount * 10 ** CURRENCY_EXPONENT[currency]);
}

export function fromMinor(amountMinor: number, currency: Currency): number {
  return amountMinor / 10 ** CURRENCY_EXPONENT[currency];
}
```

In the Prisma schema the ledger's money columns are `Int` with a `Minor` suffix: `amountMinor`, `feeMinor`, `openingBalanceMinor`, `destinationAmountMinor`. The suffix is a small thing that pays for itself. When I read `amountMinor` I never wonder whether it holds dollars or cents.

Adding integers is exact, so a balance built from a thousand movements is exactly the sum of those movements. Rounding happens at named boundaries, chiefly `toMinor`, rather than quietly inside every calculation.

### Two currencies, one manual rate

Combined totals, like net worth, need a single currency. Jasper OS converts with a **manual UGX-per-USD rate** that I set in Settings. The fallback in code is 3,800. The app never fetches a live rate.

```ts title="src/lib/calculations/money.ts"
export function convertMinor(
  amountMinor: number,
  from: Currency,
  to: Currency,
  ugxPerUsd: number = DEFAULT_UGX_PER_USD
): number {
  if (from === to) return amountMinor;
  const amount = fromMinor(amountMinor, from);
  const converted = from === "USD" ? amount * ugxPerUsd : amount / ugxPerUsd;
  return toMinor(converted, to);
}
```

At 3,800, USD 12.50 becomes UGX 47,500. Individual records always keep their own currency; conversion is only for combined totals. A live rate would make my net worth move overnight for reasons that have nothing to do with anything I did, and I would start reading noise as signal. A manual rate is stale by design, and I know exactly how stale.

## One table defines what a movement means

The hard part of personal finance software is not arithmetic. It is semantics. Is a transfer into savings an expense? Is SACCO interest a contribution? Is a loan payout income? Get these wrong and every chart downstream lies politely.

In Jasper OS the answers live in one file, `src/lib/finance/movement-rules.ts`. Its header says it plainly: if a rule is not in this file, it is not a rule. Each of the fourteen movement types has an entry like these:

```ts title="src/lib/finance/movement-rules.ts"
TRANSFER: {
  source: "required",
  destination: "required",
  crossCurrency: true,
  isIncome: false,
  expenseSign: 0,
  formula:
    "Between your own accounts. Never income or expense; only the fee costs you.",
},
LOAN_DISBURSEMENT: {
  source: "required",
  sourceClasses: ["LIABILITY"],
  destination: "required",
  destinationClasses: ASSET_CLASSES,
  crossCurrency: true,
  isIncome: false,
  expenseSign: 0,
  formula: "A loan paying out: cash goes up, and so does what you owe. Not income.",
},
```

The transaction form reads this table to decide which account fields to show, the form schema uses it for its presence checks, and the server validates against it. The `formula` string is the explanation printed under the type picker, so the explanation and the behaviour cannot drift apart.

A condensed version of the rules:

| Movement | Income | Expense | Why |
| --- | --- | --- | --- |
| Income, interest, dividend | yes | no | Interest and dividends are income, not contributions |
| Expense, fee, interest charged | no | yes | Fees on any movement are expenses too |
| Refund | no | reduces expenses | Money back is not earnings |
| Transfer between own accounts | no | only the fee | Moving money is not earning or spending it |
| Loan disbursement | no | no | Cash up, debt up |
| Principal repayment | no | only fees | Principal is not an expense |
| Currency exchange | no | only the fee | Both legs recorded, the rate difference is never income |

### Validation at the boundary

`validateMovement` reads the same table and returns a plain-language problem or `null`. A transfer needs both accounts. An adjustment touches exactly one. An account's class must fit the movement, so a loan can only pay out from a liability. A cross-currency movement must record what arrived on the other side, and a type that cannot cross currencies is told to use Exchange instead.

```ts title="src/lib/finance/movement-rules.ts"
const crossCurrency = !!(src && dest && src.currency !== dest.currency);
if (crossCurrency) {
  if (!rule.crossCurrency)
    return "This movement type cannot cross currencies; use Exchange.";
  if (input.destinationAmountMinor === null || !input.destinationCurrency)
    return "Enter the amount received on the destination side.";
}
```

The form only checks that the right fields are filled in. Ownership, account classes and currencies need real account rows, so `validateMovement` runs in the server action. The form is a convenience; the server is the rule.

## Balances are derived, never stored

There is no `balance` column that gets incremented. An account's balance is its opening balance plus the signed effect of every movement that touches it.

```ts title="src/lib/calculations/accounts.ts"
export function accountDeltaMinor(movement: MovementLike, accountId: string): number {
  let delta = 0;
  if (movement.sourceAccountId === accountId) {
    delta -= movement.amountMinor + movement.feeMinor;
  }
  if (movement.destinationAccountId === accountId) {
    delta += movement.destinationAmountMinor ?? movement.amountMinor;
  }
  return delta;
}
```

This function ignores the movement type and only looks at the legs, which is why the table's control over which legs a type may have matters so much. The fee always leaves the source side. For a cross-currency transfer the destination receives `destinationAmountMinor`, in its own currency, so a USD account loses cents and a UGX account gains shillings, both exact. Liability accounts live in negative territory and the UI shows them as an amount owed.

Deriving balances costs a loop over movements. In return, a balance can never disagree with its history, editing an old movement corrects every later balance, and "what was this account worth on the first of March" is the same function, `accountBalanceMinor`, with an `asOf` date.

When a statement disagrees, a reconciliation snapshot records the statement balance, the calculated balance and the variance. Then I decide whether to post an adjustment for the difference. The app does not decide for me.

<Note title="Legacy rows stay honest">
Before accounts existed, money rows had no account legs. When accounts arrived, those rows kept their dates and amounts, were re-typed to the nearest new meaning and flagged for review. A row with no account simply moves no balance. Inventing a history the data cannot prove would have been easier, and wrong.
</Note>

## Formulas the user can read

A savings rate is only useful if you know what it counts. Jasper OS shows the formula word for word next to the number, from the same constant that sits beside the code:

```ts title="src/lib/calculations/savings.ts"
export const SAVINGS_RATE_FORMULA =
  "Cash savings rate = net new money saved from take-home income divided by cash income received in the same period. Payroll retirement, employer contributions, interest and moves between savings accounts do not count as cash saved.";

/** Rate as a fraction (0.2 = 20%); null when there is no income to divide by. */
export function computeSavingsRate(
  contributionsUgx: number,
  incomeUgx: number
): number | null {
  if (incomeUgx <= 0) return null;
  return contributionsUgx / incomeUgx;
}
```

The numerator only counts contributions whose source is not already a savings account. Moving money from one savings account to another creates no new saving, so it is excluded, and transfers out of savings back to everyday accounts subtract.

Emergency cover works the same way: liquid emergency funds divided by essential monthly spending.

Notice the return types. With no income in a period, the savings rate is `null`, not `0`. With no emergency account or no essential-spending figure, runway is `null`. Zero would be a claim: "you saved nothing", "you have no cover". Null is the truth: there is not enough data to say. The UI shows unknown as unknown.

## Calculators get floats, behind a fence

The calculators (loan amortisation, SACCO loans, compound growth, retirement and more) are the one place floats are allowed. Compounding needs `Math.pow`, interest rates are fractions, and a projection is not a ledger entry. So calculators work in **major units**, ordinary numbers, and every money output goes through one function before it reaches the screen:

```ts title="src/lib/calculations/calculators/shared.ts"
export function roundMoney(amount: number, currency: CalcCurrency): number {
  if (!Number.isFinite(amount)) return 0;
  return fromMinor(toMinor(amount, currency), currency);
}
```

It rounds through the minor-unit boundary, so UGX results are whole shillings and USD results are whole cents. The amortisation schedule itself is computed in unrounded floats, and its last row takes whatever balance is left as principal, so the schedule closes at exactly zero instead of a stray fraction. Each row is rounded with `roundMoney` only afterwards, for display.

The shared maths has explicit zero-rate branches and never lets `NaN` or `Infinity` escape: a goal that can never be reached comes back as "unreachable", not `Infinity` months.

## The app never writes to the ledger on its own

This is the rule I would defend hardest. Nothing in Jasper OS creates a ledger entry by itself. Calculators never post. A recorded payslip does not become income until I link it to a receipt, either an existing one or one I choose to create. Turning a calculator scenario into a goal creates a goal and a linked next-action task, never a movement.

<Note title="Why no automatic entries">
The ledger is a record of what happened, and only I know what happened. An automatic entry is a guess wearing the costume of a fact. Once guesses are mixed into the ledger, every derived balance, savings rate and net-worth figure inherits them, and I can no longer tell which numbers I can trust.
</Note>

The cost is real: I enter more by hand, and a missed entry shows up as a reconciliation variance instead of being papered over. That is the right failure. A visible gap is fixable. A plausible wrong number is not.

## What I would do differently

- **Choose the column width on purpose.** Prisma's `Int` maps to a 32-bit Postgres `integer`, which caps a single value at about 2.1 billion. That is enough for a personal dashboard, but I chose the ceiling by accident. `BigInt` removes it at the price of `bigint` arithmetic everywhere, a trade that deserved a decision rather than a default.
- **Be explicit about rounding order in mixed-currency totals.** Combined totals convert and round each item with `convertMinor` before adding. That is defensible, but it can differ from converting a sum by a shilling, and the UI should say so.
- **Store the rate used alongside the totals it produced.** Exchange movements already record both legs, but saved summaries would be easier to audit if they kept the rate they used.

## The takeaway

Store money as integers in the smallest unit you actually use. Put the meaning of every movement in one table and let forms and validation read from it. Derive balances instead of storing them. Show formulas, return `null` when you do not know, and let floats into calculators only behind a rounding fence. Above all, keep the ledger for facts you confirmed.
